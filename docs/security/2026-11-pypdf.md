# New backend dependency: pypdf (issue #24)

Recorded 2026-11-06 for the dependency audit (#18). PDF text extraction for
**Extract indicators** adds one runtime dependency.

| | |
|---|---|
| Package | `pypdf` |
| Pin | `pypdf==6.21.4` (exact, in `pyproject.toml`) |
| Wheel SHA-256 | `33e4fb41ca352810eb4e9838aa0d82d6888a5f8bf682f43e99cce5faa666255c` (`pypdf-6.21.4-py3-none-any.whl`) |
| Published | 2026-10-28 |
| Transitive runtime deps | none on Python ≥ 3.11 (only optional extras, which are not installed) |
| Scope | runtime: installed in the API image |
| Use | `src/cti/services/_pdf_text_worker.py` only, in a sandboxed child process |

## Why this library and version

- Pure Python, so a parser bug can't corrupt memory. Alternatives with C or
  C++ parsers (PDFium via pypdfium2, MuPDF via PyMuPDF) are faster but carry
  native memory-safety risk, and PyMuPDF is AGPL.
- It does not execute JavaScript, render pages, or resolve external
  references or URLs. The worker reads text only, and never calls
  `decrypt()`.
- **7.0.0 was not chosen.** It was published on 2026-11-06, the day of this
  change, and is a new major version. A release only hours old has had no
  time for community review or for a compromised upload to be noticed.
  6.21.4 is the latest patch release of the mature 6.x line. Revisit the pin
  after 7.x has been out for a while.

## Advisory scan

`osv-scanner 2.7.0`, the same mode as #18's backend audit:

```sh
echo "pypdf==6.21.4" > req.txt
osv-scanner scan source --no-resolve --format json -L requirements.txt:req.txt
```

Result: **0 findings** for `pypdf==6.21.4` (2026-11-06). `pip-audit` was not
available in this environment, so the #18 cross-check was not run.

Before trusting the empty result, we checked that the scanner flags pypdf
advisories in this mode: `pypdf==5.0.0` returned 115 advisories in 67 groups.
Most of pypdf's past advisories are denial of service: unbounded loops,
memory use or decompression on crafted files. That is why the worker runs
with the limits below and does not rely on the parser being bug-free.

## Exposure and mitigations

Untrusted input: PDF attachments uploaded by authenticated users to reports.
Only admins and API keys can trigger extraction (`require_admin`).

- **Process isolation.** Every extraction runs in a fresh
  `python -I _pdf_text_worker.py` child. The parent awaits it asynchronously,
  so a stuck parse never blocks the API event loop.
- **No secrets in the child.** Its environment is empty except `LC_ALL`, and
  it never imports `cti`, so it never loads settings or the database URL.
- **No network, processes or writes.** An audit hook (`sys.addaudithook`)
  rejects `socket.*`, `subprocess.*`, `os.system`, `os.exec*`,
  `os.posix_spawn`, `os.fork`, `ctypes.*` and write-mode `open`, and
  `RLIMIT_FSIZE=0` blocks file writes as well. An audit hook is defence in
  depth, not a sandbox boundary against native code. pypdf has none.
- **Resources.** `RLIMIT_AS` 768 MiB, `RLIMIT_CPU` 20 s, `RLIMIT_CORE` 0, a
  30 s wall-clock timeout (the child is killed) and at most 2 concurrent
  children per API process.
- **Input bounds.** 20 MiB and 500 pages at most. Output is capped at 2,000,000
  characters. Encrypted PDFs fail closed, even with an empty user password.

Verified in the built image (`docker run --network none`, user `cti`): a text
PDF yields its indicators, a scanned PDF reports `pdf_no_text_layer`, and an
encrypted PDF reports `pdf_encrypted`.
